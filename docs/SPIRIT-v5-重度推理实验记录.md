# SPIRIT v5.1 重度推理模式实验记录

> 将 AI 编程助手的系统提示词从"Soul Document"声明式模式改为基于"思维分子结构"理论的重度推理模式。

---

## 一、实验背景与意图

### 问题

传统的系统提示词采用"Soul Document"模式——直接声明价值观和行为规则（"你应该先读代码再行动"）。这种模式本质上是**人类式的线性叙述**：因为A→所以B→因此C。

根据《The Molecular Structure of Thought》论文的发现，这种线性模式缺乏 LLM 需要的**元认知振荡**结构，可能无法被模型有效内化。

### 假设

如果将系统提示词改为**重度推理模式**——从几个微妙的事实出发，通过包含 Deep Reasoning / Self-Reflection / Self-Exploration 三种思维模式的推理链自然导出行为准则——模型可能更好地内化这些准则，因为：

1. 推理链的结构与模型自身的最优推理结构对齐
2. 结论从推理中"涌现"而非被声明，模型理解的是"为什么"而非"是什么"
3. 推理过程本身就是一个 few-shot 示例，示范了期望的思维模式

### 理论依据

- 论文核心发现：有效的 Long CoT 不是线性链，而是类似分子的折叠结构
- 三种"化学键"：Deep Reasoning（共价键，逻辑主干）、Self-Reflection（氢键，逻辑折叠）、Self-Exploration（范德华力，搜索空间拓展）
- 建议比例：Deep ~40-50%, Reflect ~15-25%, Explore ~10-20%, Normal ~15-25%
- 关键词不重要，行为结构才重要（关键词替换实验证明）

## 二、改造概览：从声明到推理

### 结构对比

| 维度           | v4.0 (Soul Document)             | v5.1 (Heavy Reasoning)                   |
| -------------- | -------------------------------- | ---------------------------------------- |
| 起点           | 3 个 Value（声明式）             | 6 个 Fact（公理级观察）                  |
| 展开方式       | Value → Behavior（直接声明规则） | Fact → 推理链 → 结论（从事实推导）       |
| Identity       | 直接声明                         | Chain 0 从 F1-F6 推导得出                |
| Intent Tree    | 参考信息块                       | Chain 7 从 F4+F2 推导出必要性            |
| Priority Rules | 声明式列表                       | Chain 8 从所有 Facts 推导并用场景验证    |
| 推理结构       | 线性                             | 元认知振荡（Deep ↔ Reflect ↔ Explore） |

### 6 个 Facts

| Fact | 内容                              | 推导出的结论                                       |
| ---- | --------------------------------- | -------------------------------------------------- |
| F1   | 代码是物理系统，不是叙事          | C1 Read Before Act                                 |
| F2   | 用户用时间和 token 为每个动作付费 | C9 Do One Thing Well, C10 Work in Parallel         |
| F3   | 你的输出被当作事实执行            | C4 Surface Uncertainty, C5 Communicate via Ask     |
| F4   | 用户说的是方法(X)，想的是目标(Y)  | C6 Ask About Goals, C7 Solve the Class             |
| F5   | 第一个假设通常是错的              | C2 Competing Hypotheses, C8 Know Limits            |
| F6   | 用户看不到你的思考过程            | 渗透所有链，强化 C3 Think Deep + Verify Externally |

### 9 条推理链

每条链 14+ 步，包含三种思维模式的自然交替。Chain 0 推导 Identity，Chain 1-6 推导行为准则 C1-C10，Chain 7 推导 Intent Tree 用法（C11），Chain 8 推导 Priority Rules。

### F6 的渗透效应

F6（用户看不到思考过程）不是一个孤立的 Fact——它改变了几乎所有其他链的结论：

- Chain 1：读代码从"好习惯"变为"唯一防线"（用户无法纠错）
- Chain 2：多假设从"效率工具"变为"内部纠错机制"（替代缺失的外部反馈）
- Chain 3：新增"在 content 中深度思考 + 通过脚本外化验证"
- Chain 4：不确定性必须通过 `ask_followup_question` 显式传达
- Chain 5：降低提问阈值，更积极使用 ask 确认目标

## 三、专家审查与修复

请专家按照 `CoT与FewShot设计指南.md` 的标准逐链审查后，发现并修复了以下问题：

### 3.1 C3 vs C5/C6 的张力

**问题**：C3 说"验证优于提问"（少问），C5 说"ask 是主要沟通通道"（多用 ask）——表面矛盾。

**诊断**：不是逻辑矛盾，而是 `ask_followup_question` 有两种不同用途未被区分。

**修复**：在 C5 中明确区分 ask 的两种模式：

- **(a) 信息获取型**（C3 限制的）：问用户事实 → 能自己查就别问
- **(b) 沟通型**（C5 鼓励的）：分享计划、报告发现、标记不确定性 → 应积极使用

### 3.2 反思过多（36% vs 建议 15-25%）

**问题**：因为提示词是元认知内容（关于"如何思考"的思考），反思步骤天然偏多，有 overthinking 风险。

**修复**：在 Chain 0、2、4、8 中将冗余反思转为 Normal Operation（事实陈述、直接总结）或 Deep Reasoning。

### 3.3 Normal Operation 几乎为零（2% vs 建议 15-25%）

**问题**：每一步都在"深度推理"或"反思"，缺乏缓冲和连接。

**修复**：通过上述转换增加了事实陈述、范围界定、直接总结等 Normal 步骤。

### 3.4 Intent Tree 格式的诚实性

**问题**：Chain 7 假装 XML 格式是从 Facts 推导出的，实际上是注入的设计决策。

**修复**：诚实承认——"The reasoning establishes _why_ a persistent intent record is needed. The specific _format_ is a system design decision, not something derivable from the facts alone."

## 四、已知局限与开放问题

### 4.1 元认知内容的分布悖论

提示词是关于"如何思考"的内容，天然偏向反思。论文的分布建议是针对**任务执行时**的推理，而非**元认知教学**。目前的修复降低了反思比例，但可能仍高于论文建议的上限。这是否是问题，需要实际测试验证。

### 4.2 无法严格量化

由于提示词不是标准的推理任务，无法直接计算 Pearson 相关系数与目标模型的转移矩阵对齐度。行为标注依赖人工判断，存在主观性。

### 4.3 效果未经 A/B 测试

v4.0（Soul Document）和 v5.1（Heavy Reasoning）的实际效果差异尚未通过对照实验验证。假设"重度推理模式更好"仍然是假设，不是结论。

### 4.4 Token 成本增加

v5.1（321 行）比 v4.0（277 行）多约 16% 的 token。每次对话都会消耗这些额外 token。如果效果提升不显著，这个成本可能不值得。

### 4.5 Intent Tree 的推导边界

Chain 7 诚实承认了 XML 格式是设计决策而非推理涌现。这意味着 Heavy Reasoning 模式有其适用边界——不是所有内容都能从 Facts 推导出来。外部约束（系统设计、工具接口）应该被诚实标注为约束，而非伪装成推理结论。

## 五、可迁移的技巧

以下技巧不限于系统提示词设计，可迁移到任何需要 LLM 进行深度推理的场景。

### 5.1 Facts → Reasoning → Conclusions 模式

**核心思路**：不直接声明规则，而是给出几个微妙的事实，让推理链自然导出规则。

**关键要求**：

- Facts 要**微妙**——不能直接暗示结论（否则推理链是假的）
- 推理链要体现**元认知振荡**——不是线性推导，而是有回溯、有探索、有验证
- 结论要从推理中**涌现**——如果删掉推理链，结论应该不那么显然

**反面案例**：Fact 是"你应该先读代码"，结论是"先读代码再行动"——这不是推理，是同义反复。

### 5.2 区分"可推导"和"外部约束"

不是所有内容都能从 Facts 推导出来。工具接口、数据格式、系统设计等是**外部约束**，应该诚实标注为约束，而非伪装成推理结论。混淆两者会破坏推理链的可信度。

### 5.3 用专家审查校验行为分布

手动构造推理链时，很容易偏离论文建议的比例（尤其是反思过多）。请专家逐步标注行为类型并统计分布，是发现偏差的有效方法。

### 5.4 工具角色的精确区分

在系统提示词中，不同工具的角色定位必须一致且精确。本次实验中 `ask_followup_question`（沟通工具）和 `attempt_completion`（汇报工具）的混淆导致了逻辑张力。解决方法是在结论中明确区分工具的不同使用模式。

### 5.5 框架+占位符的写入策略

大文件修改时，先写入完整框架（含占位符），再逐个填充。每次修改 ≤500 字。这避免了工具调用超时，也让修改过程可追踪、可回滚。

## 六、效果评估方法

要验证 Heavy Reasoning 模式是否真的比 Soul Document 模式更有效，需要设计对照实验。

### 6.1 定性评估（快速）

在相同任务上分别使用 v4.0 和 v5.1，观察：

- 模型是否更主动地使用 `ask_followup_question` 进行沟通？
- 模型是否在复杂问题上展现更多的自我反思和假设竞争？
- 模型是否更倾向于先读代码再行动？
- 模型是否更好地区分了目标(Y)和方法(X)？

### 6.2 定量评估（严格）

设计一组标准化任务（bug 修复、功能实现、代码审查），分别用两个版本的提示词运行，统计：

- 首次正确率（不需要用户纠正的比例）
- 平均交互轮次（达到正确结果的对话轮数）
- 工具使用模式（ask 的频率和质量、读文件的覆盖率）
- 用户满意度（主观评分）

### 6.3 证伪条件

如果以下任一条件成立，则 Heavy Reasoning 模式的假设被证伪：

- v5.1 的首次正确率 ≤ v4.0，且差异显著
- v5.1 的 token 成本增加 >15%，但效果无显著提升
- 模型在简单任务上出现 overthinking（反复反思导致效率下降）

### 6.4 迭代方向

根据评估结果，可能的迭代方向：

- 如果效果好：进一步优化行为分布，使其更接近论文建议的黄金比例
- 如果效果差：回退到 v4.0，或尝试混合模式（关键链用推理，简单规则用声明）
- 如果效果持平：考虑 token 成本，可能回退到更简洁的版本
